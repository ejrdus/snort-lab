1. 실험 개요
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  목적: 모의 금융 API 환경에서 Snort 3 커스텀 규칙의 탐지 성능을 단계적으로
        개선하고, 각 단계의 미탐지 원인을 분석하여 규칙을 고도화한다.

  방법론: "초기 규칙 작성 → 실험 → 미탐지 원인 분석 → 규칙 개선 → 재실험"
          사이클을 반복하여 탐지율을 향상시킨다.

2. 단계별 규칙 및 실험 결과
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[v1 — 초기 규칙 (Baseline)]

  Rule 1 (SID:1000001, rev:5) - SQL Injection
    pcre:"/(\'|\"|%27|%22)\s*(OR|AND|UNION|SELECT|DROP|INSERT)/i"
    → 따옴표/인코딩 뒤에 기본 SQL 키워드 6개 매칭

  Rule 2 (SID:1000002, rev:5) - 고액 이체
    pcre:"/\"amount\"\s*:\s*[5-9][0-9]{8,}/"
    → 5억~9.99억 범위만 탐지

  Rule 3 (SID:1000003, rev:5) - Brute Force
    detection_filter: track by_src, count 30, seconds 10
    → 10초 내 30회 초과 시 탐지

  Rule 4 (SID:1000004, rev:5) - Scanner UA
    pcre:"/User-Agent:.*(sqlmap|Nikto|Nmap|DirBuster|zgrab|masscan)/i"
    → 6개 도구만 탐지

[v2 — 1차 개선]

  Rule 1 (rev:6): \s* → [\s\x3b]* (세미콜론 허용), 키워드 6→14개
  Rule 2 (rev:6): [5-9][0-9]{8,} → ([5-9][0-9]{8}|[0-9]{10,}) (10억 이상 추가)
  Rule 3 (rev:6): 변경 없음
  Rule 4 (rev:6): 6→17개 도구 확장

[v3 — 2차 개선 (최종)]

  Rule 1-A (rev:7): [\s\x3b\)\(]* (괄호 허용), 키워드 18개
  Rule 1-B (rev:1): ★신규 — 숫자형/코멘트 기반 탐지 규칙 추가
  Rule 2 (rev:7): 변경 없음
  Rule 3 (rev:7): 변경 없음
  Rule 4 (rev:7): 17→21개, 실제 UA 문자열 기반 매칭

[4.2절 서술 예시 — v3 핵심 기법 상세]

  (1) SQL Injection 규칙 분리 전략

    v2까지는 단일 규칙으로 SQL Injection을 탐지하였으나,
    따옴표를 사용하지 않는 숫자형 injection(예: "1; SELECT * FROM users")과
    코멘트만 사용하는 패턴(예: "admin'--")은 탐지하지 못하였다.

    v3에서는 SQL Injection 규칙을 2개로 분리하는 전략을 적용하였다.

      Rule 1-A (따옴표 기반):
        따옴표(', ", %27, %22) 뒤에 괄호·공백·세미콜론을 허용하고,
        SQL 키워드 18개를 매칭한다.
        pcre:"/(\'|\"|%27|%22)[\s\x3b\)\(]*(OR|AND|UNION|SELECT|...)/i"

      Rule 1-B (숫자형/코멘트 기반):
        따옴표 없이 숫자 뒤에 SQL 키워드가 오는 패턴과,
        따옴표 뒤에 SQL 코멘트(--, #)만 오는 패턴을 탐지한다.
        pcre:"/(\d[\s\x3b]+(OR|AND|UNION|SELECT|...)\b|'[\s]*(\-\-|#))/i"

    이 분리의 효과는 표 5에서 확인할 수 있다.
    Rule 1-B를 추가하지 않았다면 8건(8%)이 미탐지되었을 것이다.
    단일 정규식의 한계를 규칙 분리를 통해 극복하여 100% 탐지를 달성하였다.


  (2) Scanner UA 실제 문자열 분석 기반 매칭

    v2에서는 도구 이름(예: "ffuf")을 기준으로 UA를 매칭하였으나,
    실제 ffuf 도구의 User-Agent 문자열은 "Fuzz Faster U Fool"이었다.
    마찬가지로, Burp Suite proxy의 UA는 "python-httpx"였으나
    탐지 목록에 포함되지 않았다.

    v3에서는 실제 도구가 전송하는 UA 문자열을 분석하여 매칭 패턴을 수정하였다.

      v2 미탐지 UA:
        - "Fuzz Faster U Fool v2.1.0" → 규칙에 "ffuf"만 있어 불일치
        - "python-httpx/0.24.0"       → 목록에 미등록

      v3 개선:
        - "Fuzz Faster U Fool" 패턴 추가
        - "python-httpx", "python-requests", "curl/", "libwww-perl" 추가
        - 탐지 도구 수: 17개 → 21개

    이를 통해 Scanner UA 탐지율을 90%에서 100%로 향상시켰다.


  (3) 고액 이체 정규식 범위 확장 (v2에서 해결)

    v1의 정규식 [5-9][0-9]{8,}은 첫 자리가 5~9인 경우만 탐지하여
    10억 이상(첫 자리 1~4) 금액을 놓쳤다.
    v2에서 ([5-9][0-9]{8}|[0-9]{10,})으로 수정하여
    5억 이상 전체 범위를 탐지하도록 개선하였다.

    이후 v2, v3 모두 100% 탐지를 유지하였다.


  (4) Brute Force 임계값 기반 탐지 (detection_filter)

    Brute Force 공격은 다른 3가지 유형과 달리 패턴 매칭이 아닌
    임계값 기반 탐지 방식을 사용한다.

      detection_filter: track by_src, count 30, seconds 10

    이 규칙은 동일 출발지 IP에서 10초 이내에 30회를 초과하는 요청이
    발생할 경우, 초과분에 대해 매 패킷마다 alert를 생성한다.

    탐지 alert 수가 실행마다 다른 이유는 다음과 같다.
    detection_filter는 10초 슬라이딩 윈도우 내에 도착한 패킷 수를
    기준으로 동작하므로, 네트워크 지연이나 CPU 스케줄링에 따라
    동일 윈도우 내 패킷 수가 미세하게 변동한다.
    이는 임계값 기반 탐지의 정상적인 특성이며,
    중요한 것은 30회 초과 시점부터 탐지가 시작된다는 점이다.

    본 규칙은 v1부터 v3까지 동일하게 유지되었으며,
    패턴 매칭 방식과는 달리 단순 임계값만으로도 효과적으로
    고속 반복 요청을 탐지할 수 있음을 확인하였다.
    (상세 결과는 표 6 참조)


[4.3절 서술 예시 — 고찰]

  본 연구에서는 "초기 규칙 → 미탐지 원인 분석 → 규칙 개선 → 재실험"
  사이클을 2회 반복하여 전체 탐지율을 65.7%에서 100.0%로 향상시켰다.

  특히 v3에서 적용한 SQL Injection 규칙 분리 전략은
  단일 정규식으로는 커버할 수 없는 다양한 injection 패턴을
  별도 규칙으로 보완하는 접근법의 유효성을 보여주었다.

  또한 Scanner UA 탐지에서는 도구의 공식 이름이 아닌
  실제 전송되는 User-Agent 문자열을 분석하는 것이
  탐지율 향상에 결정적이었음을 확인하였다.

  Brute Force 탐지에서는 패턴 매칭 없이 임계값 기반 방식만으로도
  고속 반복 공격을 효과적으로 탐지할 수 있었으며,
  v1부터 규칙 변경 없이 안정적으로 동작하였다.

  전 실험에서 정상 트래픽에 대한 오탐(FPR)은 0%를 유지하여,
  규칙 개선이 오탐 증가 없이 탐지 성능만 향상시켰음을 확인하였다.

  ※ 공격 유형 간 실행 순서: Scanner UA(배경) → SQLi → 고액이체 → Brute Force

표 16. SQL Injection 규칙 중복 탐지 상세
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  동일 패킷에서 Rule 1-A와 Rule 1-B가 동시 탐지된 건수: 9건

  +----------------------------+----------+------+
  | 탐지 방식                   | 탐지 건수 | 비율 |
  +----------------------------+----------+------+
  | Rule 1-A (Quote Based) 단독 |  83건    |  83% |
  | Rule 1-B (Numeric) 단독     |   8건    |   8% |
  | 두 규칙 동시 탐지            |   9건    |   9% |
  +----------------------------+----------+------+
  | 고유 탐지 합계               | 100건    | 100% |
  +----------------------------+----------+------+

  ※ Rule 1-B를 추가하지 않았다면 8건(8%)이 미탐지되었을 것.
     규칙 분리를 통해 단일 정규식의 한계를 극복하고 100% 탐지를 달성.
  ※ 9건의 중복 탐지는 패킷 내용이 두 규칙의 패턴을 동시에 충족한 경우.
     (예: 따옴표 + 숫자형 구문이 혼합된 SQLi 페이로드)


표 17. 로그 분석 핵심 결론
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  (1) v3 최종 규칙은 모든 공격 유형에서 100% 탐지율, 0% 오탐율을 달성하였다.
      572건의 alert 중 정상 트래픽에서 발생한 오탐은 단 한 건도 없었다.

  (2) Brute Force 탐지는 임계값(10초/30회) 기반으로 안정적으로 동작하였으며,
      피크 시 초당 최대 20건의 alert를 생성하여 거의 실시간 탐지 성능을 보였다.

  (3) SQL Injection 규칙 분리 전략은 실제 로그에서도 유효성이 확인되었다.
      Rule 1-B가 단독으로 탐지한 8건(8%)은 Rule 1-A만으로는 놓쳤을 공격이다.

  (4) 전체 572건 alert가 약 104초(1분 44초)에 걸쳐 발생하였으며,
      평균 5.5건/초의 탐지 처리 성능을 확인하였다.

  (5) 고유 소스 포트 500개가 공격 트래픽 500건과 정확히 일치하여,
      모든 공격 요청이 누락 없이 Snort에 의해 처리되었음을 확인하였다.
