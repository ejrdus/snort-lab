Brute Force 임계값 변경 사유 (SID:1000003)


1. 변경 이력 요약

  +--------+--------------------------------------------------+------------+---------------------------+
  | 버전   | 탐지 방식                                         | 임계값     | 대상                      |
  +--------+--------------------------------------------------+------------+---------------------------+
  | old    | 단순 문자열 매칭 (content:"dirbuster")             | 없음       | 모든 포트, 모든 트래픽     |
  | v1~v3  | detection_filter: track by_src, count 30, seconds 10 | 10초/30회 | POST /api/transfer (5000) |
  +--------+--------------------------------------------------+------------+---------------------------+


2. 왜 변경했는가

  (1) 기존 규칙(old)의 근본적 한계

    기존 local_old.rules의 SID:1000003은 Brute Force 탐지 규칙이 아니라,
    단순히 "dirbuster" 문자열이 패킷에 포함되어 있는지만 확인하는
    도구 시그니처 매칭 규칙이었다.

      alert tcp any any -> any any (msg:"DIRBUSTER DETECTED"; content:"dirbuster"; sid:1000003;)

    이 방식의 문제점:
    - Brute Force 공격 자체를 탐지하지 못함
      -> User-Agent에 "dirbuster"가 없으면 동일한 공격이라도 탐지 불가
    - 공격 빈도/속도를 고려하지 않음
      -> 1건이든 10만 건이든 동일하게 처리
    - 대상이 불특정 (any any -> any any)
      -> 어떤 서비스의 어떤 엔드포인트인지 구분 없음


  (2) v1에서 detection_filter 방식으로 전환한 이유

    Brute Force 공격의 본질은 "짧은 시간 내 비정상적으로 많은 반복 요청"이다.
    이를 탐지하려면 패턴 매칭이 아니라 임계값 기반 빈도 분석이 필요하다.

      detection_filter: track by_src, count 30, seconds 10

    이 규칙의 의미:
    - track by_src  : 출발지 IP별로 개별 추적 (다른 IP의 정상 요청에 영향 없음)
    - count 30      : 30회를 초과해야 탐지 시작
    - seconds 10    : 10초 슬라이딩 윈도우 기준


  (3) 임계값을 "10초/30회"로 설정한 근거

    공격 트래픽 파라미터 (attack_traffic.py):
    - 공격 속도: 0.05초 간격 -> 초당 약 20회 요청
    - 총 요청 수: 200건

    정상 트래픽과의 비교:
    - 정상 사용자가 10초 내에 동일 API에 30회 이상 POST를 보내는 것은 사실상 불가능
    - 공격 트래픽은 10초 내 약 200회 -> 임계값(30회)의 약 6.7배

    이 설계로 얻은 효과:

      +---------------------+----------------------------------------------+
      | 지표                | 결과                                         |
      +---------------------+----------------------------------------------+
      | 오탐 (FP)           | 정상 트래픽 1,000건 중 0건 (v1~v3 모두)       |
      | 미탐 방지           | 임계값 초과 후 매 패킷마다 alert -> 261~286건  |
      | 실시간성            | 피크 시 초당 최대 19~20건 alert               |
      +---------------------+----------------------------------------------+


  (4) v1 이후 임계값을 변경하지 않은 이유

    v1에서 설정한 count 30, seconds 10이 v2, v3 테스트에서도
    일관되게 효과적이었기 때문이다.

      +--------+------------+---------+
      | 버전   | 탐지 건수  | 오탐    |
      +--------+------------+---------+
      | v1     | 283건      | 0건     |
      | v2     | 286건      | 0건     |
      | v3     | 261건      | 0건     |
      +--------+------------+---------+

    탐지 건수 차이(261~286)는 네트워크 타이밍과 CPU 스케줄링에 따른
    슬라이딩 윈도우 내 패킷 수 변동으로, detection_filter의 정상적인 특성이다.
    핵심은 30회 초과 시점부터 탐지가 확실히 시작된다는 점이며,
    이 동작이 모든 버전에서 검증되었다.


3. 결론

  +------------+-------------------------+-------------------------------+
  | 항목       | old 규칙                | v1~v3 규칙                     |
  +------------+-------------------------+-------------------------------+
  | 탐지 대상  | 도구 이름 문자열         | 요청 빈도 (행위 기반)          |
  | OWASP 분류 | 해당 없음               | A07:2021 (인증 실패)           |
  | 오탐 제어  | 불가                    | IP별 추적 + 임계값으로 제어     |
  | 확장성     | 도구명 추가 필요         | 도구 무관, 빈도만으로 탐지      |
  +------------+-------------------------+-------------------------------+

  핵심: 도구 시그니처에 의존하는 방식에서 -> 행위 기반 임계값 탐지로 전환하여,
  공격 도구가 무엇이든 "비정상적 반복 요청" 자체를 탐지할 수 있도록 개선하였다.
